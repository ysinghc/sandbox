Boot once. Restore on demand.

Sandbox Engine is a daemon plus C and C++ client libraries. It keeps a bounded pool of pre-booted Firecracker microVMs, restores one when you ask, and returns a handle you can inspect, pause, resume, and destroy.

It is built for a single trusted operator running untrusted workloads on one host: a lab machine, a CI runner, an appliance. Each guest is jailed with chroot, seccomp, an unprivileged uid, and its own cgroup. Credentials stay on the host and are injected by a broker, so guests never hold them.

It is not a multi-tenant isolation boundary. The design and trust model are written down in Architecture and the Threat model.

The useful parts, kept sharp.

No orchestrator, no control plane, no queue you have to operate. One daemon on one host.

Restore, not boot

Snapshots plus userfaultfd demand paging mean only the pages a guest actually touches are loaded. Restored guests start at host time, and the manifest binds memory, vmstate, and rootfs by SHA-256.

Jailed before it runs

Every Firecracker process is chrooted, runs as an unprivileged uid, loads a seccomp allowlist, and starts with no_new_privs set. The guest control channel accepts only the host's vsock CID.

Limits that hold

Each VM gets its own cgroup v2 memory and CPU limits. A runaway guest cannot take the host or the daemon down with it.

Secrets stay on the host

Guests call an allow-listed upstream through a credential broker. The broker validates a per-session token and injects the real secret host-side.

From request to running guest.

A create normally resumes memory and faults in the template, then hands the VM to the caller.

  1. 01

    Restore

    The pool manager takes a restored template, or restores one from the snapshot store. The manifest binds memory, vmstate, and rootfs; a uffd handler pages memory in on demand.

  2. 02

    Contain

    The VMM manager injects the environment, places the process in a cgroup, and the jailer applies chroot, uid drop, and seccomp.

  3. 03

    Hand off

    The daemon confirms the guest is ready and returns a sandbox handle over the local protobuf API. The guest clock starts at host time, not the template's capture time.

Build it once. Ask for sandboxes.

The API is small and explicit: initialise, create, inspect, destroy. The daemon, CLI, and broker are separate binaries with one config file between them.

Prefer a release? The install script selects your architecture and checks the SHA-256 before writing anything.

Read the C and C++ API →

Needs Linux with KVM and userfaultfd. The daemon runs as root because it creates taps, device nodes, cgroups, and jails.

terminal 
# build and install from a checkout
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
$ cmake --build build -j
$ sudo cmake --install build

# stamp a template once, then start the daemon
$ sudo -E env SANDBOX_SNAPSHOT_ROOT=/var/lib/sandbox-engine/snapshots \
    build/tests/make_template
$ sudo systemctl enable --now sandboxd

# create a sandbox from the warm pool
$ sudo sandbox-cli run --template e2e --memory 512 --vcpus 1
{"event":"created","sandbox_id":1,"running":true,"memory_rss_mib":57}
