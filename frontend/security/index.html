Security

The guest is untrusted. The host is the boundary. A report that crosses that line, or that exposes a credential, is what matters most.

Supported 0.13.x Model Single trusted operator Details Threat model

Report privately.

Use GitHub's private security advisory flow. Please do not open a public issue for a vulnerability, and do not paste credentials or session tokens into a report.

Open a private advisory

Include the version (sandboxd --version), the host architecture, the exact steps to reproduce, and the impact you believe is possible. A minimal proof of concept helps more than a long write-up.

Scope, in one paragraph

Sandbox Engine is an isolation layer for one trusted operator running untrusted code on one host. It is not a multi-tenant isolation boundary. Once code is inside the guest, it owns the guest; containment within the VM is not the security boundary. The boundary is guest to host, guest to network, and caller to daemon.

In scope

  • A guest escaping the Firecracker jail or reaching the host filesystem.
  • A guest reading upstream credentials, or bypassing the broker allow-list.
  • An unprivileged local user driving the daemon outside allowed_uids.
  • A tampered snapshot or release archive being accepted as valid.
  • Privilege escalation in sandboxd, the jailer, or the broker.

Not in scope

  • Code doing destructive things inside its own VM. The VM is the blast radius.
  • Confidentiality from the host operator, who owns the host and the credentials.
  • Network anonymity. Egress policy limits destinations, not content.
  • Prompt injection in code supplied by a caller. That is an application concern.

What is already in place

A restored Firecracker process runs chrooted, as an unprivileged uid, under a seccomp allowlist, with no_new_privs set and a per-VM cgroup. Guest egress is dropped except for the host broker, which validates a per-session token and injects real credentials host-side. The guest control channel accepts only connections from the host vsock CID. Snapshots are checked against a SHA-256 manifest before restore. The daemon allow-lists peer uids on its Unix socket.

The privileged suite (jailer, seccomp, restore, vsock, cgroup, nftables) runs on self-hosted KVM hosts in CI and the job fails if any test skips.

The threat model records the threats, mitigations, and open items row by row. The implementation log tracks the hardening backlog.

Known limitations

  • The daemon is still a single root trusted computing base. Privilege separation is planned for V2.
  • Releases include SHA-256 checksums but are not cryptographically signed yet.
  • Per-tenant quotas are future work; this remains a single-operator design.

Release integrity

Every archive has a matching .sha256 file on the release page. Verify it before extracting. If a checksum does not match, stop and report it privately.

terminal 
$ sha256sum -c sandbox-engine-0.13.0-linux-x86_64.tar.gz.sha256
