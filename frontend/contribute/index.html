Contribute

Sandbox Engine is small on purpose. Changes should stay focused, keep the design honest, and leave the tests better than they found them.

License GPL-2.0-only Language C11 / C++17 Start Open issues

Good changes are legible.

Explain what changed and why. If the implementation has to differ from the design, write the deviation down rather than letting the docs drift.

  • Follow the existing style and file layout.
  • Keep commits atomic with imperative subjects.
  • Update docs and the changelog in the same change.
  • Say how privileged tests were validated.

Read the full contributing guide before opening a pull request.

Build and test

The default build is enough for development. Most end-to-end tests need root, /dev/kvm, and guest assets; the unprivileged subset runs anywhere the dependencies are installed.

terminal 
# release build and the unprivileged suite
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
$ cmake --build build -j
$ ctest --test-dir build --output-on-failure

# sanitizer pass
$ cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug \
    -DSANDBOX_SANITIZE=address,undefined
$ cmake --build build-asan -j
$ ctest --test-dir build-asan --output-on-failure

The privileged tests run on a lab host with real KVM and Firecracker. docs/TESTING.md explains the split and the runner prerequisites.

Pull request checklist

  1. Branch from master.
  2. Keep the change focused. Separate refactors from behavior changes.
  3. Pass build, unprivileged tests, ASan/UBSan, and the fuzz smoke job.
  4. Update the affected design section, docs/, and CHANGELOG.md.
  5. In the PR, state exactly which privileged tests you ran and how.

Where to help

Fix a bug

Pick an open issue, reproduce it, and include a regression test where the suite allows one.

Browse issues →

Harden the engine

Seccomp auditing, privilege separation, vsock payload authentication, and per-tenant quotas are open in the V2 backlog.

See the backlog →

Improve the docs

If a guide was wrong while you set up the host, fix it. Deployment details are the most valuable kind of correction.

Open docs/ →

Report a bug

Include expected vs. actual behavior, exact commands, uname -a, sandboxd --version, and relevant log lines.

Open an issue →

Security-sensitive reports

Do not open a public issue for a vulnerability. Use the private advisory flow described on the security page.
